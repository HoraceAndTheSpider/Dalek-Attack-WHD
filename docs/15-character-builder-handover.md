# 15 – Character Builder Handover / START HERE

## Current state

Research stages 1–3 have established that a component-based Dalek Attack Character Builder is feasible.

No Character Builder UI has been implemented yet.

The existing character extraction/editor should remain unchanged while the component model is proven.

---

## Do not re-open these resolved questions

Treat the following as established project decisions unless new evidence directly contradicts them:

1. A complete playable-character bank is 45 × 32×40 frames = 28,800 bytes.
2. The 288×200 sheet is 9×5 frames.
3. Frame numbering starts at 0, top-left.
4. Frames 28–44 are right-facing counterparts of 0–16 and should normally be generated by horizontal flip.
5. Frame groups are:

   - 0–1 idle/fire
   - 2–7 six-phase horizontal locomotion
   - 8 crouch
   - 9–11 horizontal jump/fall
   - 12–15 upward reach/jump-to-grab/overhead-wire
   - 16 crouch-fire
   - 17–20 ladder/face-on climb
   - 21–24 rear-facing four-step movement
   - 25–27 front/back interaction
   - 28–44 right-facing counterparts

6. Frame 25 is front-facing and used on character select.
7. Frame 26 is doorway/rear-facing interaction.
8. Frame 27 is crouching to find hidden objects.
9. Do not use arbitrary rotation/scaling to build pixel-art limbs.
10. Keep the builder separate from `dalek_character_tool.py` until an original character has been reconstructed successfully.
11. Coats/garments may have front/rear layers, but should only be split where layering requires it.
12. Very small sonic-screwdriver artwork is best allowed as a hand+equipment composite.
13. Standalone component outlines can differ from assembled outlines; seam/outline handling is required.
14. Do not ask the user to cut up all 45 frames. The supplied representative references are intended to minimise manual prep.

## Things to avoid

- Do not treat a visually similar region as an exact reusable asset without indexed-pixel comparison.
- Do not infer component identity from colour alone.
- Do not use OCR-driven automatic analysis of the user's cut-up sheets when manual layout metadata is clearer.
- Do not quantise arbitrary RGB artwork into the palette without explicit controlled conversion.
- Do not silently clip assets at frame boundaries.
- Do not regenerate/overwrite manual frame overrides without warning.
- Do not merge experimental builder code into the established editor prematurely.
- Do not claim a precise reduced asset count before the representative masks are analysed.

## Current overall objective

The project is not attempting procedural animation.

It is attempting to turn the original 45-frame requirement into a manageable set of reusable **pixel-art building blocks**, while preserving:

- original Dalek Attack poses;
- exact frame alignment;
- indexed palette;
- black-outline style;
- costume layering;
- game-ready output.
